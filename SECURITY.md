# ProxyCTL — security model

ProxyCTL is a **single-operator** control plane. An authenticated admin is
*intentionally* trusted with `ssh` + `kubectl`-equivalent power — that's the
job. The protections below are about who *becomes* that operator, and about
not over-exposing the cluster to the public internet.

## Auth

- First run generates a one-time **bootstrap token** in memory, logged once.
  It only unlocks the `/api/auth/setup` claim — it never authenticates a
  request.
- Claim writes a JWT signing key + bcrypt admin record into the
  `proxyctl-auth` Kubernetes Secret. Thereafter auth is a JWT (HS256, 8h).
- Recovery: `kubectl delete secret proxyctl-auth` + rollout restart → a
  fresh bootstrap token on the next pod log.
- The `DISABLE_AUTH` dev escape hatch refuses to start on a non-loopback
  bind.

## RBAC footprint

ProxyCTL holds the minimum it needs, and no more. **It has no cluster-wide
write access to any resource** — every workload it creates lives in its own
namespace.

- **ClusterRole `proxyctl-reader`, read-only** — `namespaces`, `services`,
  `pods`, `endpoints` (`get`/`list`/`watch`), so the UI's target picker can
  browse any namespace and compute each Service's "X/Y ready" badge. Also
  `nodes` (`get`/`list`), which the Storage step uses to generate an
  `/etc/exports` line restricted to exactly the node InternalIPs — and to warn
  later when a newly added node isn't covered.
- **ClusterRole, one cluster-scoped write** — `storageclasses`, `create` only
  (no `update`, no `delete`). Gateway keypair PVCs bind through a class whose
  `pathPattern` nests them under the operator's chosen folder; a changed folder
  is a new class name, so create-if-missing is sufficient.
- **Namespaced Role `proxyctl-gateway-mgr`** (ProxyCTL's own namespace) — the
  full lifecycle of everything ProxyCTL deploys: the per-game `wg-gw-*`
  gateways *and* the `cloudflared` connector that carries web-app traffic
  (Deployments, Secrets, PVCs, Services). Plus `pods` `create`/`delete` for the
  Storage step's short-lived NFS probe pod, `pods/exec` `create` to read each
  gateway's self-generated WireGuard **public** key, and read-only `pods/log` +
  `events` so a failed mount surfaces its actual error in the UI.
- **Namespaced Role `proxyctl-auth`** — `secrets` `create` (Kubernetes can't
  filter `create` by `resourceNames`, since the name is in the request body,
  not the URL path), plus `get`/`update`/`patch` scoped to the single
  `proxyctl-auth` Secret. The blast radius of the broad `create` is bounded:
  ProxyCTL's namespace only ever holds ProxyCTL itself.

ProxyCTL never holds standing droplet credentials — its SSH keypair is
generated by the Setup wizard and the private half lives 0600 on the PVC, never
returned by an API — and it never holds cluster-admin.

## Droplet SSH access

The droplet's `sshd` is pubkey-only (`PasswordAuthentication no`) regardless
of anything below — that's the actual authentication boundary. The Setup
wizard's "Restrict SSH access" step then picks exactly one of two mutually
exclusive ways to cut down who can even *reach* it:

- **Option A — tunnel-only (recommended).** A firewall-level `PROXYCTL-SSH`
  iptables chain drops any new port-22 connection whose source isn't an
  allow-listed WireGuard tunnel peer (the control tunnel, or a registered
  personal-access device). This is enforced before the TCP handshake even
  completes, so unauthorized traffic never reaches sshd at all.
- **Option B — public-IP allow-list.** sshd-level only (`Match Address` /
  `DenyUsers` in an sshd_config drop-in), no firewall rule involved. SSH stays
  reachable from the internet, but auth is refused for any source not on the
  list — which also means this option depends on the operator keeping that
  list current; an IP change breaks their own access until they update it.
  ProxyCTL's own management access is unaffected either way, since it always
  prefers a dedicated control-tunnel connection over the public IP.

**fail2ban** is a separate, additional layer that bans repeat failed-auth
source IPs, and it matters in *both* modes — just differently. Under
Option B (or no lockdown), it's front-line: anything on the internet can
reach sshd and try. Under tunnel-only, outside traffic never reaches sshd —
but **tunnel-connected peers do**, so a device holding a valid WireGuard
config without the right SSH key (your own laptop mid key-setup, or a
stolen tunnel config) still generates real auth failures and earns real
bans. Defense-in-depth behind an already-authenticated connection. The
ban policy (attempts, window, permanent vs. timed) is tunable — and the
whole service can be switched off — from the app's fail2ban card, which is
shown in every mode. Note the flip side: that policy applies to your own
devices too; a mistyped key path can ban your own tunnel IP, which is
exactly what the card's "Allow back in" button undoes (ProxyCTL's own
management connection uses a separate tunnel peer, so it stays up to do
the unbanning).

**Leftover manual UFW rules.** Some droplets were locked down by hand — a UFW
rule restricting port 22 to a specific IP — before ProxyCTL managed SSH
access at all. That rule is invisible to and unmanaged by either option
above and breaks the operator's access the moment that IP changes. The setup
step detects a rule like this (a specific IP/CIDR only — never a wide-open
one) and can remove it: it snapshots the real UFW rule files first, verifies
a fresh SSH connection still works immediately after the change, and reverts
to the exact prior rules if it doesn't.

## Web Routes — Cloudflare Tunnel, no ingress controller

Web apps do not ride the droplet, and **no ingress controller is involved at
all** — yours or ProxyCTL's. Each web route is a hostname in a Cloudflare
Tunnel whose connector runs inside your cluster:

1. ProxyCTL creates the tunnel through the Cloudflare API (`cfd_tunnel`) and
   fetches its connector token.
2. It applies `proxyctl-cloudflared` — a Secret holding that token plus a
   2-replica Deployment — into **its own namespace**, covered by the existing
   namespaced Role. The connector needs zero Kubernetes RBAC of its own: it
   only dials outbound to Cloudflare's edge and reaches Service ClusterIPs,
   which any pod can do.
3. It pushes the tunnel's ingress rules via the API (`config_src=cloudflare`),
   mapping each public hostname to one in-cluster Service, with a terminal
   `http_status:404` catch-all.
4. It upserts a proxied (orange-cloud) CNAME per hostname →
   `<tunnel-id>.cfargotunnel.com`.

Security properties that fall out of this:

- **Nothing is reachable that you didn't add.** The tunnel's ingress list *is*
  the allowlist, and anything not matching a rule hits the `404` catch-all. A
  Service being in the cluster does not expose it.
- **No inbound ports, no public IP, no certificates on your side.** The
  connector dials out; TLS terminates at Cloudflare's edge, which also
  provides WAF and DDoS protection.
- **Your internal (`.lan`) routing is never in the path.** Traffic goes
  Cloudflare edge → `cloudflared` → the backend Service's ClusterIP directly.
- **The connector token is a Secret in ProxyCTL's namespace**, base64-encoded
  into the manifest and injected via `secretKeyRef`. Rotating it is a
  re-apply — `kubectl apply` reconciles and the changed token rolls the pods.

> **Historical note:** earlier versions routed web apps through a dedicated
> public Traefik instance, with ProxyCTL rendering a Traefik `IngressRoute`
> per route and holding a cluster-wide write grant on
> `traefik.io/ingressroutes`. That design is gone — there is no Public Traefik
> setup step, no IngressRoute rendering, and no Traefik permission in
> `k8s/proxyctl.yaml`. If you deployed a `traefik-public` instance for
> ProxyCTL under the old model, it is no longer used and can be removed.
